# Local (on-device) AI for classifying, tagging and sorting files on Apple Silicon Macs — state as of October 2026

Research method note: ~40 web searches plus direct reads of GitHub READMEs/docs. Many vendor domains (apple.com, digikam.org, immich.app, noodlesoft.com, cyme.io, macstories.net) were unreachable from the research sandbox, so where a vendor page could not be opened the finding is sourced to a search-result excerpt or a secondary report and flagged. Nothing below was verified by running the software.

## Key Question 1: Open-source "AI file organizer" projects (llama-fs, Local File Organizer, etc.) — maturity, models, runtimes

### Takeaway
The well-known open-source organizers (LlamaFS, Local File Organizer) are 2024 hackathon-grade projects that rename/re-folder files from an LLM/VLM summary; both are effectively unmaintained (last meaningful updates 2024–Aug 2025), run via Ollama or Nexa SDK, and offer a dry-run/review step because the classification is a free-text LLM guess, not a trained classifier. The more active 2025–2026 energy is in narrower tools: metadata/keyword writers (exif-ai, VisionTagger, Photo Assisted Keywords, Tag Your Photos) that write XMP/IPTC rather than moving files, running Qwen3-VL / Gemma 4 / Llama 3.2-Vision on Ollama or MLX.

### Cited Findings
- LlamaFS (iyaja/llama-fs): "self-organizing file manager" that renames and sorts files by content; batch mode (POST a directory to a FastAPI server, get a suggested tree) and watch mode (daemon learns from your renames). Backend is Llama 3 via **Groq (cloud) by default**; "incognito mode" routes to **local Ollama**; **Moondream** (via Ollama) for images; **Whisper** for audio. Requires Python 3.10+, Electron/React frontend; MIT; ~5.8k stars, 102 commits, 53 open issues; swapping Groq→Ollama "requires editing the code directly" and is listed as a TODO; needs a Groq API key for default setup — [GitHub README](https://github.com/iyaja/llama-fs)
- LlamaFS repo last push reported as Aug 8, 2025 (≈5.7k stars, 378 forks) — [gittrend aggregator](https://gittrend.io/repo/iyaja/llama-fs)
- Local File Organizer (QiuYannnn): uses **Llama 3.2 3B** (text) and **LLaVA v1.6 Vicuna-7B** (images) through **Nexa SDK**'s `NexaTextInference`/`NexaVLMInference`; "no data leaves your computer"; supports png/jpg/jpeg/gif/bmp, txt/docx/md, xlsx/csv, ppt/pptx, pdf; sort by content/date/type; dry-run mode; needs Python 3.12, Conda, Git, Tesseract OCR; macOS Metal build documented; **last release v0.0.2, September 2024**; 3.3k stars, 33 commits, 26 open issues; prompts are changed by editing Python source; roadmap items (chat "Copilot Mode", audio/video, duplicate detection) unfinished — [GitHub README](https://github.com/QiuYannnn/Local-File-Organizer)
- exif-ai (tychenjiajun/exif-ai): Node CLI that "write[s] AI-generated image descriptions and/or tags directly into the metadata of image files"; Ollama provider needs no API key, **default model `llama3.2-vision`**, `OLLAMA_BASE_URL` configurable; writes descriptions to XPComment/Description/ImageDescription/Caption-Abstract and tags to **Subject, TagsList, Keywords** (fields configurable); `--dry-run`, `--tag-prompt`, `--avoid-overwrite`, `--repeat`; no watch mode; GPL-2.0; 274 commits, 28 stars, no tagged releases — [GitHub](https://github.com/tychenjiajun/exif-ai)
- Ollama has official **Qwen3-VL** models; local variants include `qwen3-vl:4b` and `qwen3-vl:8b`; the Python client passes an image path with a chat message — [Ollama blog via search](https://ollama.com/blog/qwen3-vl); [Apatero guide](https://apatero.com/blog/ollama-qwen-3-vl-models-local-guide-2025)
- MLX route: `mlx-community/Qwen3-VL-8B-Instruct-4bit` converted with mlx-vlm 0.3.4; run with `python -m mlx_vlm.generate --model ... --image <path> --prompt ...` — [Hugging Face](https://huggingface.co/mlx-community/Qwen3-VL-8B-Instruct-4bit)
- mlx-vlm (Blaizzy/mlx-vlm) is "a package for inference and fine-tuning of Vision Language Models (VLMs) and Omni Models" on Apple MLX; supported families include Qwen2-VL, Qwen2.5-VL, **Qwen3-VL**, Qwen3.5/3.8, **Gemma 4**, Gemma 3n, LLaVA, LLaVA-OneVision, Idefics3, Molmo, PaliGemma, Pixtral, **Florence-2**, DeepSeek-OCR, MiniCPM-o, Phi-4 Multimodal, **Moondream2/3**; CLI `mlx_vlm.generate` and an OpenAI-compatible `mlx_vlm.server --port 8080` — [GitHub](https://github.com/Blaizzy/mlx-vlm)
- Google's Gemma docs show Gemma 4 running on Mac via `mlx_lm` (text) and `mlx_vlm` (vision) with `mlx-community/gemma-4-e2b-it-4bit`, plus `mlx_vlm.server` exposing an OpenAI-compatible endpoint on localhost:8080; Gemma 4 takes text, audio and image input, 256K context — [ai.google.dev Gemma MLX page](https://ai.google.dev/gemma/docs/integrations/mlx?hl=hi)
- Gemma 4 release date reported as April 2, 2026 (one review) vs "2026-05" (aggregator); sizes reported inconsistently (E2B, E4B, 26B MoE, 31B vs e2b/e4b/12b/26b/31b) — [llmconfigurator review](https://llmconfigurator.com/en/blog/gemma-4-complete-guide-google-open-source-model); [local-llm.net](https://www.local-llm.net/models/gemma-4/)
- Ollama README (Oct 2026) headlines `ollama run gemma4`; install on macOS via `Ollama.dmg` or the install script — [GitHub ollama/ollama](https://github.com/ollama/ollama)
- Llama 3.2 Vision 11B is ≈7.9 GB to pull; on a 16 GB Mac mini M4 an estimator puts it at ~8.5 GB (Q4_K_M) to ~10.8 GB (Q6_K) of ~12 GB usable — [llmconfigurator](https://www.llmconfigurator.com/pl/can-i-run/llama-3-2-vision-on-mac-mini-m4-16gb)
- Gemma 3 Ollama download sizes: 4B 3.3 GB, 12B 8.1 GB, 27B 17 GB (checked Sept 2026) — [needtoknowit](https://needtoknowit.com.au/blog/best-ollama-models-to-download.md)
- Newer commercial Mac tagging apps (details in KQ3): **VisionTagger** (Synendo; local VLM, GGUF model + projector, ExifTool for XMP; macOS 26 required, 16 GB RAM recommended; ~$30–35 one-time) — [ifun.de](https://www.ifun.de/visiontagger-ki-erstellt-bildbeschreibungen-und-schlagwoerter-auf-dem-mac-283011/), [AlternativeTo](https://alternativeto.net/software/visiontagger/about); **Tag Your Photos** (Gemma 4 12B via MLX, writes IPTC keywords into the Apple Photos library) — [Product Hunt](https://www.producthunt.com/products/tag-your-photos/built-with); **Photo Assisted Keywords** (12B model via MLX, writes XMP sidecars for RAW) — [Product Hunt](https://www.producthunt.com/products/photo-assisted-keywords)
- A PyPI package (May 2026) is listed as "Tag macOS Photos library images using local Gemma model for searchable tags" — [PyPI user page](https://pypi.org/user/kurok/)
- Hazel-like CLI "hazelnut" watches folders and applies move/copy/rename/run-command rules (could be a glue layer for a script-based organizer) — [Terminal Trove](https://terminaltrove.com/hazelnut/)

### Inferences
- Neither flagship "AI organizer" is a sound daily-driver in 2026: both froze in 2024, both bundle the whole pipeline (model runtime + file moves) and both depend on outdated model stacks (Llama 3 / LLaVA 1.6 / Nexa SDK). The practical 2026 pattern is to treat the VLM as a captioner/keyworder and leave file placement to deterministic rules (Hazel, scripts), which is what the newer apps do.
- For a 16 GB Apple Silicon Mac, a Q4 8B-class VLM (Qwen3-VL 8B, Gemma 3 12B, Llama 3.2-Vision 11B) fits; 27B+ needs 32 GB or more. 24–36 GB machines can run Gemma 4 26B MoE / Qwen3-VL 32B-class models comfortably (size inference from download sizes above).
- Ollama is the lowest-friction runtime (one HTTP API on port 11434, usable from Hazel shell scripts); MLX via mlx-vlm is faster on Apple Silicon and gets new model families first, but is a Python environment to maintain.

### Gaps
- No independent accuracy benchmarks of LLM-driven file renaming/categorization were found; HN/Reddit discussions of llama-fs could not be retrieved (search returned only aggregators).
- Exact current versions/release dates of mlx-vlm and exif-ai were not shown on their GitHub pages.
- Gemma 4's official size lineup and license could not be confirmed from Google's own announcement (not reachable); sources conflict.

## Key Question 2: Apple's built-in options (Photos people, Visual Look Up, Spotlight, Apple Intelligence in macOS 26/27, Shortcuts "Use Model", Foundation Models, Vision) and what is exportable

### Takeaway
Apple gives you on-device face recognition (Photos People), on-device image classification/OCR (Vision framework, used by Spotlight and the Shortcuts "Extract Text" action) and, since macOS 26, an on-device LLM reachable from Shortcuts ("Use Model") and from Swift (Foundation Models framework, which gained image input at WWDC 2026). Photos' person names are exportable as plain keywords (XMP dc:Subject) via "Export IPTC as XMP" or far more flexibly via osxphotos (which also writes MWG/Microsoft face regions to XMP sidecars), but nothing in Apple's stack sorts files into folders by itself.

### Cited Findings
- Shortcuts "Use Model" (macOS 26+): lets you "use an Apple Intelligence model, either on-device or Private Cloud Compute, or ChatGPT in custom shortcuts"; a model "can provide input to an action, parse the output of an action, and more"; the on-device option handles "simple requests without the need for a network connection"; Apple Intelligence "is not available on all Mac models or in all languages or regions"; a newer version of the page references macOS 27 and lists "Cloud" and "Cloud Pro" model options — [Apple Support: Use Apple Intelligence in Shortcuts on Mac](https://support.apple.com/guide/shortcuts-mac/mchl91750563/mac) (page unreachable from sandbox; quoted from search excerpt)
- MacStories: third-party developers only got the local Foundation model, while Shortcuts users can prompt either Apple model (on-device or PCC) — [MacStories](https://www.macstories.net/notes/i-have-many-questions-about-apples-updated-foundation-models-and-the-great-use-model-action-in-shortcuts/) (unreachable; from search excerpt)
- Shortcuts Library has Apple Intelligence shortcuts including "Create Memory in Photos" (describe a memory → Apple Intelligence + Photos builds it); no published shortcut that tags or sorts photos was found — [Matthew Cassinelli](https://matthewcassinelli.com/new-shortcuts-library-apple-intelligence)
- Foundation Models framework at WWDC 2026: image input added — prompts can include an `ImageContent` alongside text, initialized from UIImage/CGImage/CVPixelBuffer/file URL; Vision tools (text/barcode recognition) usable by the model; image analysis described as on-device only; Apple also announced a Python SDK, a model abstraction layer, and "a second, more capable on-device model for higher-end iPhone, iPad, and Mac" supporting text, image and speech — [byteiota](https://byteiota.com/apple-foundation-models-wwdc-2026-multimodal-python-sdk/); [Callstack](https://callstack.com/blog/on-device-ai-after-wwdc-2026-whats-new); [blakecrosley](https://blakecrosley.com/blog/foundation-models-image-input-ios-27); [chatforest](https://chatforest.com/builders-log/ios-27-foundation-models-multimodal-image-input-builder-guide/) — all third-party write-ups; Apple docs not reachable
- macOS 27 ("Golden Gate") Photos: no redesign; new Tools panel (Reframe/Spatial Reframing, Extend, upgraded Clean Up requiring Apple Intelligence), star ratings (off by default), "rebuilt search index shared with Spotlight and Mail"; Shortcuts gains natural-language shortcut creation; Apple Intelligence "not available in all languages or regions" — [9to5Mac](https://9to5mac.com/?p=1070528); [Apple Support macOS 27 Apple Intelligence](https://support.apple.com/en-mk/guide/mac-help/mchl46361784)
- macOS 26 Tahoe Spotlight accepts more natural-language queries and new actions; "most tasks are run on-device … heavier AI features handled via Private Cloud Compute" — [Tom's Guide](https://tomsguide.com/computing/macos/i-review-macbooks-for-a-living-3-macos-tahoe-26-features-im-most-excited-about); [AppleMagazine](https://applemagazine.com/hands-on-with-macos-tahoe-26-faster-cleaner/)
- One user report that Photos' natural-language search on Mac returned nothing for "black shirt" — [MacRumors forum](https://forums.macrumors.com/tags/ai-search/) (single anecdote)
- Vision framework: classification, text recognition, saliency, animal/human detection available since macOS Catalina; `VNClassifyImageRequest` returns label strings with confidence; face detection is a separate request; Apple's current sample "Classifying images for categorization and search" targets macOS 15+/Xcode 16; "all processing occurs on-device" — [MBS plugin docs](https://mbsplugins.eu/VisionClassifyImage.shtml); [createwithswift](https://createwithswift.com/detecting-faces-in-images-with-the-vision-framework); [Apple sample (Scribd mirror)](https://www.scribd.com/document/837572213/Classifying-images-for-categorization-and-search-Apple-Developer-Documentation)
- Shortcuts OCR: a shortcut of "Receive Any input" → "Extract Text from Shortcut Input" → "Copy to Clipboard" can be driven from Terminal with `shortcuts run ocr-text -i <image>` — [greg.technology](https://blog.greg.technology/2024/01/02/how-do-you-ocr-on-a-mac.html); [billmill](https://notes.billmill.org/link_blog/2024/01/mac_shortcut_to_OCR_text.html)
- Apple Photos export: "Export Unmodified Original" with "Export IPTC as XMP" writes a sidecar whose keywords include people names (XMP dc:Subject); face rectangles are **not** exported; for JPEGs you then need exiftool to copy sidecar fields into the file — [Lightroom Queen forum](https://www.lightroomqueen.com/community/threads/how-do-i-import-mac-face-tages-as-lrc-people-keywords.42716/); [PhotoPrism Apple guide: "Keywords (include people)"](https://docs.photoprism.app/user-guide/use-cases/apple); [OSXDaily](https://osxdaily.com/2023/03/26/export-iptc-as-xmp-in-photos-for-mac-explained-what-does-exporting-iptc-as-xmp-do/); [ExifTool forum: face names in XMP subject bag](https://exiftool.org/forum/index.php?msg=47658)
- Apple Photos (macOS 13.4) does not read people tags from a third-party sidecar; workaround is copying names into `-XMP-dc:Subject` inside the JPEG — [Apple Community](https://discussions.apple.com/thread/254932358?page=1)
- osxphotos (RhetTbull): `--exiftool` writes EXIF:ImageDescription, XMP:Description, XMP:Title, XMP:TagsList, IPTC:Keywords, XMP:Subject, **XMP:PersonInImage**; `--person-keyword` = "Use person in image as keyword/tag when exporting metadata"; `--album-keyword`, `--keyword-template '{name,DEFAULT}'`; `--sidecar xmp` exports "Description, Title, Keywords/Tags, Subject (set to Keywords + PersonInImage), PersonInImage, CreateDate, ModifyDate, GPS…, **Face Regions (Metadata Working Group and Microsoft Photo)**"; `--exiftool-merge-keywords/--exiftool-merge-persons` — [osxphotos export.py](https://raw.githubusercontent.com/RhetTbull/osxphotos/main/osxphotos/cli/export.py)
- osxphotos is tested macOS 10.12.6→Sequoia, lists macOS 27.0 (Golden Gate) in its compatibility table, Tahoe 26.x "limited testing", shared albums unreadable on 26.x; Python 3.10–3.14; `push-exif` writes metadata back to originals inside the Photos library; `{person}` template field = "Person(s) / face(s) in a photo" — [osxphotos README](https://github.com/RhetTbull/osxphotos)
- Tag Your Photos (3rd-party) writes IPTC keywords into the Photos library database so they are "indexed by Spotlight" — [completeaitraining listing](https://completeaitraining.com/ai-tools/tag-your-photos/)

### Inferences
- The exportable unit from Apple Photos is "person name as keyword". A Shortcuts/osxphotos job can therefore run `osxphotos export --person-keyword --exiftool` (or `--sidecar xmp`) and a downstream rule engine can branch on XMP:Subject/PersonInImage. osxphotos is the only tool found that also emits standards-based face regions.
- "Use Model" on-device is text-centric in macOS 26; as of macOS 27 the Foundation Models API accepts images, so a Swift script (or Shortcuts if the action now accepts images — unverified) could caption/classify images with zero third-party models, but at the capability level of a ~3B on-device model.
- Vision framework's built-in classifier plus face detection are free and fast on the Neural Engine but return generic taxonomy labels, not identities.

### Gaps
- Could not confirm whether the Shortcuts "Use Model" action accepts image input in macOS 27 (Apple pages unreachable; search found no example).
- No Apple documentation retrieved for Foundation Models image input (only third-party write-ups).
- No confirmation of whether macOS 27 Photos' natural-language search runs fully on-device or how accurate it is.

## Key Question 3: Commercial Mac apps with local AI tagging/organization (Hazel, Excire, Peakto, Mylio, Tonfotos, Photo Mechanic, Lightroom Classic, digiKam) — cost, XMP/IPTC write-back, Apple Photos integration

### Takeaway
Excire Foto 2027 (US$249 one-time, released June 16 2026) and digiKam 8.8 (free) are the strongest fully-local "keyword + face" catalogers that write standard XMP; Peakto is Mac-only and syncs with Apple Photos/Lightroom but is subscription-first ($189 "unlimited" with 12 months of updates); Mylio Photos+ is subscription-only ($99.99/yr); Tonfotos is a cheap one-time face-sorter ($39/$99) with weak Apple Silicon acceleration; Hazel 6 ($) adds on-the-fly OCR but no AI — it is the rule/move layer, not the classifier; Lightroom Classic has local face recognition but is subscription; Photo Mechanic has no face recognition.

### Cited Findings
- **Hazel 6**: new features are on-the-fly text recognition ("A rule can examine the text within graphics and PDFs if they have not been OCRed"), encrypted-PDF passwords (keychain), revert processed files, Custom List Attributes; 6.0.2 added option to run text recognition even if file already has text ("as needed" default); 6.1 adds Liquid Glass look for macOS 26 and requires macOS 13+ — [Noodlesoft What's New](https://www.noodlesoft.com/?p=1997); [Hazel 6.0.2 notes](https://www.noodlesoft.com/?p=1894); [heise](https://heise.de/-10000567); [TidBITS Hazel 6.1](https://talk.tidbits.com/t/hazel-6-1/32328)
- Hazel shell scripts: usable as condition or action; receive the file path as `$1`; run with a limited environment so "always specify the full path to any program" and quote `"$1"` — [Noodlesoft: Using Shell Scripts](https://www.noodlesoft.com/?p=977)
- Hazel "Contents contain" uses Spotlight and falls back to "Contents contain match" (on-the-fly recognition, no text layer written) — [MacPowerUsers forum](https://talk.macpowerusers.com/t/hazel-not-reading-pdf/21862)
- No source found describing any Apple Intelligence/LLM integration in Hazel (three searches) — absence of evidence
- **Excire Foto 2027**: released June 16, 2026 for Windows/macOS; one-time license **US$249 / €229 / £229 / CHF 229** (launch promo US$219/€199); upgrade from 2024 US$99, from 2025 US$79; 14-day trial; new text-in-image recognition (signs, bib numbers), World Map, filter bar/timeline, Survey culling view, focus peaking, OneDrive/Nextcloud sharing, keywords from folder names, video; "All AI processing stays on your computer" — [PhotoWorkout](https://www.photoworkout.com/?p=222334); [Dead Pixels Society](https://thedeadpixelssociety.com/prc-debutes-excire-foto-2027-ai-powered-photo-management-app/); [Skylum marketplace](https://marketplace.skylum.com/excire-foto-2027); [B&H](https://www.bhphotovideo.com/c/product/1982018-REG/excire_excire_foto_2027.html)

- Excire face features: name tags and people collections; people search by age/gender/number of subjects; "facial-recognition technology works privately on your PC"; ships separate Apple Silicon (ARM) and Intel builds — [Excire 2025 release](https://excire.com/en/excire-foto-2025-release/); [fotowissen.eu](https://www.fotowissen.eu/?p=121128)

- **Phototheca** (macOS) also offers automatic face scanning and person naming — [search result mention only](https://lunarship.com/manual/face-recognition/)

### Inferences
- Of the one-time-license options, Excire Foto 2027 is the most complete local "AI keyword + face + text-in-image" tool, but keywords must be explicitly saved to files and Apple Photos integration is import-only (not verified). digiKam is the only free tool that combines face recognition, 1,000-class auto-tagging and standards-based metadata writing, at the cost of a Qt UI and database maintenance.
- Hazel remains purely the action layer; its OCR makes receipt/invoice sorting possible with plain keyword rules, while any AI classification must be bolted on via "Run shell script" (see KQ4).

### Gaps

## Key Question 4: Practical pipeline (watch folder → local VLM → XMP via exiftool → Hazel/script moves) — state of the art and where it breaks

### Takeaway
All the pieces exist and are documented individually (Hazel/launchd/Shortcuts folder trigger → Ollama or mlx-vlm HTTP endpoint → exiftool writes XMP-dc:Subject/IPTC:Keywords → Hazel rule matches keyword and moves). The weak link is semantic: a VLM produces scene/object keywords and confident-sounding guesses, and no source found shows it reliably distinguishing specific individuals; sorting "wife's family" vs "mother's side" needs a face-identity layer (digiKam/Excire/Apple Photos/InsightFace) feeding names into the same keyword fields.

### Cited Findings
- Ollama Qwen3-VL accepts an image path in a chat message from the Python client; local tags `qwen3-vl:4b`/`8b` — [Ollama blog](https://ollama.com/blog/qwen3-vl); [Apatero](https://apatero.com/blog/ollama-qwen-3-vl-models-local-guide-2025)
- mlx-vlm provides `mlx_vlm.server --port 8080` with `/v1/chat/completions` (OpenAI-compatible) so any script can call a local VLM over HTTP — [mlx-vlm GitHub](https://github.com/Blaizzy/mlx-vlm)
- exif-ai is a ready CLI for "Ollama → write Subject/TagsList/Keywords" with `--dry-run` and custom `--tag-prompt` — [exif-ai GitHub](https://github.com/tychenjiajun/exif-ai)
- IVTagger (ONNX WD14 taggers, not a VLM) writes tags to EXIF/IPTC/XMP via ExifTool, with overwrite/append modes — a non-LLM, deterministic alternative — [civitai article](https://civitai.com/articles/26143)
- VisionTagger: outputs JSON/CSV/TXT and **Finder tags**; XMP/in-file writing via separately installed ExifTool; custom fields with per-field prompts and types (Boolean/Text/List) — [ifun.de](https://www.ifun.de/visiontagger-ki-erstellt-bildbeschreibungen-und-schlagwoerter-auf-dem-mac-283011/); [AlternativeTo](https://alternativeto.net/software/visiontagger/about)
- Tag Your Photos deliberately keeps labels general when uncertain ("bird" rather than species) — a vendor acknowledgement of VLM over-specificity — [completeaitraining](https://completeaitraining.com/ai-tools/tag-your-photos/)
- Hazel runs shell scripts as conditions or actions with `$1` = file path, limited PATH — [Noodlesoft](https://www.noodlesoft.com/?p=977)
- hazelnut (CLI) watches folders and applies move/copy/rename/run-command rules — [Terminal Trove](https://terminaltrove.com/hazelnut/)
- OnDevice OCR Pro (commercial, one-time) offers a hot-folder that OCRs new files with Apple Vision in the background plus Shortcuts integration — [MacRumors forum (developer post)](https://forums.macrumors.com/threads/ondevice-ocr-pro-an-offline-text-recognition-automation-software.2485273/)
- mac-ocr (open source CLI) OCRs images/PDFs with Apple Vision, writes searchable PDFs and per-image .txt (`mac-ocr *.png -o '[dir]/[name].txt'`) — [WeAreDevelopers](https://www.wearedevelopers.com/magazine/756-tool-showcase-mac-ocr-extract-text-from-images-locally-on-your-computer)
- Sidecar fragility: XMP sidecars are matched by filename, so renaming/moving in Finder breaks the link — [DxO forum](https://forum.dxo.com/t/why-are-my-tags-not-working-after-copying-from-icloud/37121?page=4)
- Apple Photos only reads people/keywords embedded in the JPEG (`-XMP-dc:Subject`), not from third-party sidecars — [Apple Community](https://discussions.apple.com/thread/254932358?page=1)
- Paperless-ngx CPU-only test: Gemma 4 E4B median 25.8 s per suggestion, 6.6–7.6 GiB RAM; reasoning models lost the "no reasoning" instruction and produced hundreds of extra tokens or 400 errors (v3.1.3) — [jacar.es](https://jacar.es/en/paperless-ngx-3-local-ai-ollama/)
- LlamaFS claims <500 ms per operation in watch mode, but via Groq cloud inference and caching — [LlamaFS README](https://github.com/iyaja/llama-fs)

### Inferences
- A robust 2026 Mac pipeline: (1) Hazel or a Shortcuts folder automation fires on new files; (2) a script POSTs the image to Ollama (`qwen3-vl:8b`) or mlx-vlm server with a constrained prompt ("return JSON with fields: scene, people_count, document_type, keywords"); (3) exiftool writes `XMP-dc:Subject`/`IPTC:Keywords` (embedded for JPEG/HEIC, sidecar for RAW); (4) Hazel rules keyed on those keywords (and on OCR text for PDFs) move files. Embedding rather than sidecars avoids the rename-breaks-sidecar failure.
- Throughput on an M-series Mac is seconds per image for 8B VLMs (and ~26 s/doc for a 4B-class text model on CPU per the Paperless test), so backlog processing of tens of thousands of photos is an overnight-to-days job, not interactive.
- Failure modes evidenced by sources: hallucinated specifics (species, brands), inconsistent label vocabulary run-to-run, reasoning-model chatter polluting structured output, and total inability to assign personal identity. Constrain output (fixed label list, JSON schema), keep a dry-run/review step (as every organizer tool does), and never let the VLM pick the destination folder for people-based categories.

### Gaps
- No end-to-end published Hazel+Ollama+exiftool recipe was found; the composition above is inferred from the individual tools' documentation.
- No quantitative accuracy data for VLM keywording of personal photo libraries; no Reddit/HN threads retrieved before the search budget ran out.
- Shortcuts "Folder" automation trigger availability on macOS 26/27 not verified from Apple docs.

## Key Question 5: Face recognition — which local tools learn named people and auto-assign, and can that drive folder sorting / keyword tagging

### Takeaway
Named-person learning that then auto-assigns new photos exists locally in Apple Photos, digiKam (YuNet+SFace, cumulative training), Excire Foto, Mylio, Lightroom Classic, Tonfotos, Immich (DBSCAN clustering on a NAS) and Python stacks (InsightFace/DeepFace/face_recognition). Only osxphotos (from Apple Photos), digiKam, Excire and Mylio surface the result as file metadata (keywords and, for osxphotos/digiKam, MWG face regions) that a folder-sorting rule can consume; Immich and Apple Photos themselves keep names in their databases.

### Cited Findings
- Apple Photos person names → keywords (`--person-keyword`), `XMP:PersonInImage`, and `--sidecar xmp` face regions (MWG + Microsoft Photo) via osxphotos — [osxphotos export.py](https://raw.githubusercontent.com/RhetTbull/osxphotos/main/osxphotos/cli/export.py); Photos' own export puts names in XMP dc:Subject but no rectangles — [Lightroom Queen](https://www.lightroomqueen.com/community/threads/how-do-i-import-mac-face-tages-as-lrc-people-keywords.42716/)
- digiKam: YuNet detection + SFace embeddings, KNN+SVM ensemble (8.6.0); recognition improves with more confirmed faces; background re-recognition when faces are confirmed (8.7.0); Accuracy sliders; People tags in tag tree — [digiKam 8.6.0](https://digikam.org/news/2025-03-15-8.6.0_release_announcement); [digiKam 8.7.0](https://www.digikam.org/news/2025-06-30-8.7.0_release_announcement/); [people_view.rst](https://raw.githubusercontent.com/KDE/digikam-doc/master/left_sidebar/people_view.rst); maintenance "Rebuild all training data" / "Reset and clear all faces" — [maintenance_faces.rst](https://raw.githubusercontent.com/KDE/digikam-doc/master/maintenance_tools/maintenance_faces.rst)
- Excire: name tags, people collections, people search by age/gender/count — [Excire](https://excire.com/en/excire-foto-2025-release/)
- Mylio: face recognition "even if partially obscured", names assignable, "face tags are saved as part of your photo metadata"; reviewer calls it "hands down the best I've used" — [Mylio](https://mylio.com/face-recognition/); [Photofocus](https://photofocus.com/software/the-most-amazing-face-recognition-tool-youve-never-tried/)
- Lightroom Classic: stacks similar faces; naming a stack tags all photos — [Adobe](https://helpx.adobe.com/ie/lightroom-classic/desktop/organize-photos-in-lightroom-classic/face-recognition.html)
- Tonfotos: license "unlocks all names"; Apple Silicon acceleration weak per vendor — [Trustpilot](https://ca.trustpilot.com/review/tonfotos.com); [Tonfotos community](https://community.tonfotos.com/d/350-support-of-apple-m1-m4-cpu-will-make-the-indexing-faster)
- Immich facial recognition: detection on preview → recognition embeddings in DB → modified DBSCAN; settings Minimum detection score (don't go below 0.5), Maximum recognition distance (keep 0.3–0.7; lower for twins), Minimum recognized faces; default model "typically considered the best", smaller model for constrained systems; nightly job; page does not say names are written to files — [Immich facial-recognition.md](https://raw.githubusercontent.com/immich-app/immich/main/docs/docs/features/facial-recognition.md)
- Immich ML hardware acceleration: ARM NN (Mali), CUDA, ROCm, OpenVINO, RKNN; "Only Linux and Windows (through WSL2) servers are supported"; **no Apple/Core ML backend** — [Immich ml-hardware-acceleration.md](https://raw.githubusercontent.com/immich-app/immich/main/docs/docs/features/ml-hardware-acceleration.md); CPU build is the default `ghcr.io/immich-app/immich-machine-learning` image — [DeepWiki summary](https://deepwiki.com/immich-app/immich/5.2-hardware-acceleration)
- Immich smart search: CLIP-family models incl. multilingual nllb / xlm / siglip2 options; VectorChord on Postgres; model change requires reprocessing — [Immich searching.md](https://raw.githubusercontent.com/immich-app/immich/main/docs/docs/features/searching.md)
- Python DIY: InsightFace-MCP = "fully local, offline facial recognition search system for your photo library" (InsightFace + FAISS; LM Studio-oriented, Windows paths) — [glama.ai](https://glama.ai/mcp/servers/ee2ufebe9f); Facesift matches images against a reference photo with the `face_recognition` library, cross-platform, early-stage (17 commits) — [GitHub](https://github.com/Th3Tr1ckst3r/Facesift); DeepFace wraps VGG-Face/FaceNet/ArcFace/Dlib with auto weight download — [pythonlib.ru](https://pythonlib.ru/en/library-theme93); a write-up used DeepFace with one reference photo to split 10 years of photos into "me"/"others" folders — [vc.ru](https://vc.ru/life/2683983-kak-ya-ispolzoval-neyroset-dlya-sortirovki-10-let-fotografiy); ImageSorter moves portraits into per-face directories — [GitHub mirror](https://backiee.wasmer.app/http_github_com/nkhilgaba/ImageSorter)

### Inferences
- For a Mac-centric user already in Apple Photos, the lowest-effort "identity → folder" path is: keep naming people in Photos (on-device, free), then schedule `osxphotos export --person-keyword --exiftool` (or `--sidecar xmp`) to a staging folder and let Hazel route on `XMP:PersonInImage`. For a file-system-first library, digiKam's People tags + metadata sync play the same role and are free.
- Immich on a NAS gives good clustering but, run on a Mac, is CPU-only inside Docker; names stay in Immich's DB, so it is a browsing layer rather than a file-sorting engine.
- Family-side sorting ("wife's family" vs "mother's side") is a mapping from recognized names → group, which belongs in the rule layer (Hazel list attribute / script lookup table), not in the model.

### Gaps
- No primary digiKam source confirming the exact XMP schema (mwg-rs vs MP RegionInfo) written for faces in 8.x.
- Whether Immich can export person names to file metadata (e.g., via its API + exiftool) was not researched.
- No head-to-head accuracy figures across these face engines were found.

## Key Question 6: Document side — local OCR and classification of PDFs/scans (Paperless-ngx, Apple Vision OCR, local LLM) to split receipts/invoices from personal documents

### Takeaway
Paperless-ngx 3.0 (22 July 2026) ships native, opt-in local AI (Ollama backend) that suggests title/tags/correspondent/document type and can auto-apply them via workflows (3.1+), which makes a NAS-hosted Paperless the most mature local "business vs personal" document classifier; on the Mac itself, Hazel 6's built-in OCR plus keyword rules, or Apple Vision OCR via Shortcuts/mac-ocr feeding a local LLM, cover the simpler cases.

### Cited Findings
- Paperless-ngx 3.0.0 released **22 July 2026** with built-in AI: suggestions for title, tags, correspondent, document type; chat over one document or the archive; vector index for similar documents; 3.1.0 added a workflow action to apply suggestions automatically; 3.0.5 (1 Aug 2026) split suggestion cache per model/endpoint; 3.2.0 (19 Sep 2026) made automatic inbox suggestions switchable off; disabled by default — [WZ-IT](https://wz-it.com/en/blog/paperless-ngx-ai-setup/); [jacar.es](https://jacar.es/en/paperless-ngx-3-local-ai-ollama/)
- Official config: `PAPERLESS_AI_ENABLED` (default false); `PAPERLESS_AI_LLM_BACKEND` = `openai-like` | `ollama`; `PAPERLESS_AI_LLM_MODEL` default `llama3.1` for ollama; `PAPERLESS_AI_LLM_ENDPOINT` required for ollama; `PAPERLESS_AI_LLM_EMBEDDING_BACKEND` = openai-like | huggingface | ollama (defaults `sentence-transformers/all-MiniLM-L6-v2` / `embeddinggemma`); `PAPERLESS_AI_LLM_CONTEXT_SIZE` 8192; `PAPERLESS_AI_LLM_REQUEST_TIMEOUT` 120 s; `PAPERLESS_AI_LLM_EXTRA_PARAMS` e.g. `{"reasoning_effort":"none"}`; `PAPERLESS_LLM_INDEX_TASK_CRON` default `10 2 * * *` — [paperless-ngx docs/configuration.md](https://raw.githubusercontent.com/paperless-ngx/paperless-ngx/main/docs/configuration.md)
- Paperless wiki guidance: prefer an instruction/chat model that follows structured output; start with the smallest model that fits; multilingual embeddings `intfloat/multilingual-e5-small/base` or `BAAI/bge-m3`; "starting points, not benchmarks"; changing embedding model requires rebuilding the index — [AI Model Recommendations wiki](https://github.com/paperless-ngx/paperless-ngx/wiki/AI-Model-Recommendations)
- CPU-only experience: Gemma 4 E4B ≈25.8 s median per suggestion, 6.6–7.6 GiB RAM; reasoning models misbehave — [jacar.es](https://jacar.es/en/paperless-ngx-3-local-ai-ollama/)
- Paperless-AI (clusterzx) has shown "This repo is currently not maintained" since March 2026 and its author doubts continuing given official integration — [Paperless-AI README](https://cdn.jsdelivr.net/gh/clusterzx/paperless-ai@main/README.md); [WZ-IT](https://wz-it.com/en/blog/paperless-ngx-ai-setup/)
- paperless-gpt (icereed) still offers Ollama-based titles/tags/correspondents/custom fields and Ollama-vision OCR; README example uses `qwen3:8b` — [GitHub](https://github.com/icereed/paperless-gpt)
- Hazel 6 can match text inside non-OCRed PDFs/images on the fly; passwords for encrypted PDFs; "Contents contain match" is the on-the-fly path — [Noodlesoft](https://www.noodlesoft.com/?p=1997); [MacPowerUsers](https://talk.macpowerusers.com/t/hazel-not-reading-pdf/21862)
- Apple Vision OCR from the command line: Shortcuts "Extract Text" run via `shortcuts run <name> -i file`; mac-ocr CLI batch-writes .txt and searchable PDFs; OCR output "can contain false information", hyphens/line breaks need cleanup — [greg.technology](https://blog.greg.technology/2024/01/02/how-do-you-ocr-on-a-mac.html); [WeAreDevelopers mac-ocr](https://www.wearedevelopers.com/magazine/756-tool-showcase-mac-ocr-extract-text-from-images-locally-on-your-computer); [screensnap](https://www.screensnap.pro/blog/extract-text-from-image-mac)
- Foundation Models (macOS 27) can call Vision text/barcode recognition as tools and take screenshots/documents as image input on-device — [byteiota](https://byteiota.com/apple-foundation-models-wwdc-2026-multimodal-python-sdk/)
- Local File Organizer needs Tesseract for PDF/image text — [GitHub](https://github.com/QiuYannnn/Local-File-Organizer); mlx-vlm supports DeepSeek-OCR — [mlx-vlm](https://github.com/Blaizzy/mlx-vlm)

### Inferences
- Business-vs-personal splitting is well suited to Paperless-ngx: consume folder on the NAS → OCR → AI suggests correspondent/document type/tags → workflow auto-applies → storage-path rules file receipts/invoices separately. Point `PAPERLESS_AI_LLM_ENDPOINT` at an Ollama instance on the Mac (or on the NAS if it has enough RAM) with a small non-reasoning instruct model and set `reasoning_effort: none`.
- For scans that must stay on the Mac, Hazel 6 OCR + keyword/regex rules ("Invoice", "Rechnung", VAT IDs) handles most receipts deterministically; an LLM step is only needed for ambiguous documents and should return a fixed label set.
