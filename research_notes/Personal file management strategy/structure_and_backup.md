## Key Question 1: Folder structure vs. metadata/tag-based organization for photos — do practitioners recommend a date-only hierarchy with people/events handled by keywords, collections and face tags? Why do per-family / per-event folder trees break down?

### Takeaway
The dominant practitioner pattern is a single, shallow, chronological folder tree (Year / YYYY-MM-DD[_short-description]) as the *physical* layer, with every other dimension (people, events, trips, "best of", family branch) expressed as keywords, collections/albums and face tags that live in metadata or the catalog. Forum evidence shows per-event/per-subject trees fail because a photo can only live in one folder, event names are hard to recall by date, and keyword/folder schemes drift and are never back-applied to older material; the fix is a small, stable keyword vocabulary plus virtual collections rather than more folders.

### Cited Findings
- Lightroom Classic's three organizing tools have distinct roles: folders mirror the physical disk location (moving a photo between folders in LrC moves the file on disk); collections are virtual, do not move or duplicate files, and one photo can sit in dozens of collections while existing in one folder; keywords are searchable metadata that travel with exported files — [Markus Hagner Photography, "How to Organize Photos Using Folders, Collections and Keywords in Lightroom Classic" (Aug 2026)](https://markus-hagner-photography.com/how-to-organize-photos-using-folders-collections-and-keywords-in-lightroom-classic/)
- Same source's division of labor: folders handle "permanent storage organization, backup management, chronological filing, separating different clients or years"; collections handle "project groupings, portfolio selections, albums for clients"; keywords handle "content-based searching, subject identification, location tagging" — [Markus Hagner Photography](https://markus-hagner-photography.com/how-to-organize-photos-using-folders-collections-and-keywords-in-lightroom-classic/)
- Practitioners who run date folders keep event memory by appending a short description to the dated folder name, e.g. "2024-11-16 Lovely Lake birds", so chronology sorts correctly while the event is still readable — [BCG Forums, "How Do You Organize Your Collections in Lightroom Classic?"](https://bcgforums.com/threads/how-do-you-organize-your-collections-in-lightroom-classic.40376)
- Other users import each trip into a collection ("Sometrip 2024"), keep per-location collections grouped in a collection set, and maintain yearly "Best of" collections (birds, family, trips) — event grouping is done by collections, not folders — [BCG Forums](https://bcgforums.com/threads/how-do-you-organize-your-collections-in-lightroom-classic.40376)
- Lightroom Classic cannot sort folders by capture date; collections sort only by name or kind, so a YYYY-MM-DD prefix is what makes alphabetical order equal chronological order — [Adobe Community, "sort folders or collections by date"](https://community.adobe.com/questions-675/sort-folders-or-collections-by-date-982327)
- Failure mode of keyword sprawl: one user reports keywords "kept adding complexity, the system became hard to maintain, and many pictures in older folders weren't updated with the newer keywords"; another admits "too many specialized keywords" made the keyword library cumbersome — [Talk Photography, "Folders in Lightroom"](https://www.talkphotography.co.uk/threads/folders-in-lightroom.638165/)
- Counter-view: a sports photographer argues finding by event name is faster than remembering the month; a separate Adobe thread shows a user wanting to keep the event link while reducing folder count; an Adobe community expert notes keywords become necessary either way, e.g. to find one person across many family events — [Adobe Community thread 15025537](https://community.adobe.com/adobe-users/15025537); [Adobe Community, "how do you handle repetitive file organization around lightroom classic"](https://community.adobe.com/questions-675/how-do-you-handle-repetitive-file-organization-around-lightroom-classic-1640585)
- Scott Kelby's approach (secondhand, via forum users citing his Lightroom book/videos): keep all photos in one master catalog and organize with collection sets, collections and keywords rather than folder trees — [Adobe Community, "How to organise Lightroom by collections instead of dated folders"](https://community.adobe.com/t5/lightroom-classic-discussions/how-to-organise-lightroom-by-collections-instead-of-dated-folders/m-p/11059211); [Lightroom Killer Tips, "The Truth About This Whole Cataloging Thing"](https://lightroomkillertips.com/the-truth-about-this-whole-cataloging-thing/)
- Jeff Carlson (Take Control of Your Digital Photos) says he rarely uses regular albums and prefers smart albums that gather images based on criteria; the book's import chapter stresses applying keywords to all incoming photos at import, then touching up afterward — [TidBITS chapter excerpt](https://tidbits.com/?p=13946); [jeffcarlson.com chapter 7 note](https://jeffcarlson.com/2013/08/05/chapter-7-of-take-control-of-your-digital-photos-now-available/)
- Peter Krogh's The DAM Book (O'Reilly, 2006; 2nd ed. 2009 adding Lightroom) describes a "unified digital photo archive" with chapters on "information structures (file and directory naming)" and on applying metadata/keywords, based on Krogh's own archiving system — [Wikipedia: Peter Krogh (photographer)](https://en.wikipedia.org/wiki/Peter_Krogh_(photographer)); [PhotographyBLOG review](https://www.photographyblog.com/pages/reviews/reviews_dam_book.php); [LWN review](https://lwn.net/Articles/161354/)
- Library of Congress personal-archiving guidance for photos: identify all photos (cameras, computers, removable media, web), choose the keepers and where several versions exist "save the one with highest quality", give individual photos descriptive file names, and add descriptions — [Library of Congress, digitalpreservation.gov personal archiving: photos](https://www.digitalpreservation.gov/personalarchiving/photos.html); [LOC Perspectives on Personal Digital Archiving e-book summary](https://genealogyblog.com/?p=25675)
- Generic archival file-naming guidance applicable to photo folders: date-first YYYY-MM-DD sorts chronologically; zero-pad months/days and sequence numbers (0001…); put the date in the file name as well as the folder because files get moved and lose folder context; hyphens/underscores instead of spaces; pick one convention and be consistent — [Smithsonian Libraries file naming PDF](https://library.si.edu/sites/default/files/tutorial/pdf/filenamingorganizing20180227.pdf); [Excel Campus naming tips](https://www.excelcampus.com/tips/naming-files/); [Appalachian State file organization](https://confluence.appstate.edu/spaces/ATKB/pages/321585303/File+Organization)
- dpBestflow was a Library of Congress–funded ASMP project (funded August 2007 under NDIIPP) covering digital photography best practices "from camera settings to archival file formats" — [Harvard Library Innovation Lab on dpBestflow](https://lil.law.harvard.edu/blog/2009/11/19/dpbestflow-org); [Wetpixel on dpBestflow](https://wetpixel.com/articles/dpbestflow-provides-resources-for-image-makers)

### Inferences
- A date-based tree is the only hierarchy that is (a) objectively derivable from EXIF without human judgment, (b) stable (a photo's date never changes, but "which family / which event" is a judgment that changes as families merge and events recur), and (c) auto-creatable by every importer (Lightroom, Photo Mechanic, digiKam, Image Capture, Immich all offer YYYY/YYYY-MM-DD import templates). That is why practitioners converge on it even when they disagree about everything else.
- Per-family/per-event trees fail for a structural reason the forum posts illustrate: a Christmas photo with both sides of the family present must be filed in one place, so either it is duplicated (dedup problem later) or one family's "folder" is incomplete. Keywords/face tags are many-to-one; folders are one-to-one.
- The "folder date + short slug" compromise ("2024-11-16 Lovely Lake birds") preserves 80% of the event-recall benefit at zero metadata cost and is still machine-sortable; the slug can later be converted into a keyword with exiftool (see Question 6).
- Keyword failure modes in the forums are vocabulary problems, not keyword problems: keep the vocabulary to a controlled list (People, Place, Event-type, Family-branch) and apply at import in batch, as Carlson recommends.

### Gaps
- Could not retrieve the actual text of The DAM Book's folder/naming chapter or its "bucket" concept; searches returned only reviews and the Wikipedia summary. The claim that Krogh recommends date-based buckets could not be verified from a primary source in this session.
- Could not retrieve dpBestflow.org's own file-naming / organization pages (search returned only pages about the project, not its content).
- No peer-reviewed or survey-style evidence on folder-vs-metadata was found; all evidence is practitioner/forum/author guidance.

## Key Question 2: Which metadata standards make organization portable across apps (XMP sidecar vs embedded, IPTC keywords, hierarchical keywords, MWG face regions, ratings/labels), and which apps read/write them?

### Takeaway
Flat keywords in `XMP-dc:Subject` (mirrored to `IPTC:Keywords`), ratings in `XMP:Rating`, and dates in EXIF are the only fields that survive every app tested in the sources. Hierarchical keywords and face regions are fragmented: Lightroom uses `lr:HierarchicalSubject`, digiKam uses `digikam:TagsList`, Microsoft used `MicrosoftPhoto:LastKeywordXMP`, and the MWG 2.0 spec defines `mwg-kw:Hierarchy` for keywords and `mwg-rs:Regions` for faces; Lightroom Classic and digiKam both write MWG regions, Immich reads tags from digiKam/LR/IPTC fields in priority order but face-name import is unconfirmed, Apple Photos exports names only as keywords (regions stay in its database), and exiftool is the tool everyone uses to translate between them.

### Cited Findings
**Keyword fields and hierarchy**
- Lightroom stores hierarchy in `lr:HierarchicalSubject` and flattened keywords in `dc:subject` (Dublin Core); Exiv2 documents the `lr` namespace as "Adobe Lightroom hierarchical keywords" — [Daminion, "Hierarchical keywords in Lightroom: be careful"](https://daminion.net/articles/tips/hierarchical-keywords-in-lightroom-be-careful/); [Exiv2 XMP lr tags](https://exiv2.org/tags-xmp-lr.html)
- digiKam uses its own `XMP-digikam:TagsList`; XnView lists five keyword forms it can write: IPTC flat, XMP-dc flat, XMP-lr hierarchical, XMP-digikam hierarchical, XMP-Microsoft hierarchical — [XnView newsgroup](https://newsgroup.xnview.com/viewtopic.php?p=164228)
- A Shotwell/GNOME issue (2011–2013) records the digiKam maintainer preferring the digiKam namespace, calls `lr:HierarchicalSubject` a de-facto standard, and lists `Xmp.MicrosoftPhoto.LastKeywordXMP` as another hierarchy location; the MWG guidelines suggest `mwg-kw:Hierarchy` — [GNOME Shotwell issue 3142](https://gitlab.gnome.org/GNOME/shotwell/-/issues/3142)
- MWG 2.0 spec requires hierarchical keyword path elements to be *flattened* so each node becomes its own `dc:subject` entry (Daminion calls this "questionable") — [Daminion](https://daminion.net/articles/tips/hierarchical-keywords-in-lightroom-be-careful/)
- ExifTool's MWG tag reference documents `mwg-kw` hierarchical keywords (unrolled to depth 6) and the MWG Regions structure — [ExifTool MWG Tags](https://exiftool.sourceforge.net/TagNames/MWG.html)
- DxO writes every standalone keyword as a single-level hierarchy, "not standard", which can confuse other software — [DxO forum, "Exact rules for the creation and use of sidecar files"](https://forum.dxo.com/t/exact-rules-for-the-creation-and-use-of-sidecar-files/36580?page=5)
- Files commonly carry three keyword sets at once: legacy IPTC, XMP flat, XMP hierarchicalSubject (Adobe namespace); apps that read only one can break hierarchies — [Image Alchemist metadata tag](https://imagealchemist.net/tag/metadata)
- Phil Harvey (ExifTool author) recommends writing `XMP:Subject` rather than `IPTC:Keywords` when adding keywords — [ExifTool forum msg 49360](https://exiftool.org/forum/index.php?msg=49360)

**Face regions**
- The MWG Regions structure is "the most standard tag to hold facial recog regions"; Microsoft's older Regions format is "pretty much dead" since Photo Gallery was discontinued — [ExifTool forum msg 64723](https://exiftool.org/forum/index.php?msg=64723)
- Lightroom Classic: face regions and names are written to the file/sidecar when you Save Metadata to XMP (manually or via Catalog Settings > Metadata > auto-write XMP); on export, names go out as `XMP:Subject`/`IPTC:Keywords` and full face region data is kept only if "Remove Person Info" is unchecked; the keyword export "does not identify the name with the face" — [Adobe Community, "Possible to embed face data with LR Classic"](https://community.adobe.com/t5/lightroom-classic-discussions/possible-to-embed-face-data-with-lr-classic/m-p/12238821); [Adobe Community, "exporting face tag metadata"](https://community.adobe.com/questions-680/exporting-face-tag-metadata-931469)
- Lightroom Classic stores a name both as an MWG region and as a keyword; importing Picasa files (region only) imports the region and name but attaches no keyword; a 2015 report says LR "does NOT read and process existing XMP-mwg-rs written by other software"; workaround is exiftool `-xmp:subject+<regionname` before import — [Adobe Community, "face image region data written according to XMP-mwg-rs but not read by LR"](https://community.adobe.com/t5/lightroom-classic-discussions/face-image-region-data-written-according-to-xmp-mwg-rs-but-not-read-by-lr/m-p/7144734/highlight/true)
- Unnamed detected faces cause count mismatches (5 RegionName vs 6 RegionArea entries); a June 2025 post says Lightroom has no API for face data so older plugins may not work, but face data in the file remains readable with ExifTool — [Adobe Community, "how can i export people tags with associated faces to the web"](https://community.adobe.com/t5/lightroom-classic-discussions/how-can-i-export-people-tags-with-associated-faces-to-the-web/m-p/15371194)
- Lightroom (cloud) does not export face tags the way Classic does (Adobe community manager statement) — [Adobe feature request](https://community.adobe.com/feature-requests-681/p-export-face-tag-metadata-people-names-from-lightroom-cloud-661024)
- digiKam: a user describes digiKam storing face regions as `XMP-mwg-rs` (Name, RegionList, Type) plus some `XMP-MP` properties; older digiKam kept rectangles only in its DB (KDE bug 277429, 2011); a later reader of bug 328018 saw the people tag written but mwg-rs not displayed in digiKam's viewer — [Nextcloud forum](https://help.nextcloud.com/t/how-does-photos-2-handle-existing-face-tags/149285); [KDE bug 277429](https://bugs.kde.org/show_bug.cgi?id=277429); [KDE bug 328018](https://bugs.kde.org/show_bug.cgi?id=328018)
- Inspect regions with `exiftool -s -XMP-mwg-rs:all File.jpg`; RegionAreaX/Y are center points as fractions of image size — [ExifTool forum msg 64734](https://exiftool.org/forum/index.php?msg=64734)
- Only one writable `RegionName` tag exists in ExifTool, so group prefix (mwg-rs) does not matter when writing — [ExifTool forum msg 93277](https://exiftool.org/forum/index.php?msg=93277)
- ExifTool can convert Picasa .ini face data to XMP-mwg-rs / XMP-MP regions — [ExifTool forum msg 37237](https://exiftool.org/forum/index.php?msg=37237); [picasa2xmp project](https://github.com/bufemc/picasa2xmp)

**digiKam sidecar settings (official docs)**
- Write modes: "Write to XMP sidecar only", "Write to item and XMP sidecar", "Write to XMP sidecar for read-only item only" (RAW/video); default sidecar name `image1.dng.xmp`, with an option for the `image1.xmp` form "used by many commercial programs"; "Read from sidecar files" makes digiKam ignore embedded metadata; "Lazy Synchronization" defers writes; disabling timestamp updates "can introduce issues with external applications that use file timestamp properties" — [digiKam Metadata Settings](https://docs.digikam.org/setup_application/metadata_settings.html)

**Immich / PhotoPrism**
- Immich: during the metadata extraction job it reads `.xmp` files and during the Sidecar Write job writes back; parsed fields are title, description, date, rating, tags; for tags it checks `digiKam:TagsList`, `lr:HierarchicalSubject`, `IPTC:Keywords` in that priority order; sidecar must be `IMG_0001.jpg.xmp` or `IMG_0001.xmp` (not `myphoto_meta.xmp`); external-library DISCOVER job associates sidecars sitting next to media; a SYNC job rescans existing sidecars — [Immich docs: XMP sidecars](https://docs.immich.app/features/xmp-sidecars); [Immich docs: tags](https://docs.immich.app/features/tags/)
- Immich face regions: a 2023 feature request says Immich wrote coordinates but not person info; a 2025 discussion points to "enable face import from EXIF/Sidecar" in admin metadata settings, but a user reports the person name still not shown — unresolved — [Immich discussion 4348](https://github.com/immich-app/immich/discussions/4348); [Immich discussion 15076](https://github.com/immich-app/immich/discussions/15076)
- PhotoPrism: built-in Exif parser, a "simple XMP reader" for standalone `.xmp` sidecars (self-described initial proof-of-concept, subset of fields), plus ExifTool for embedded XMP/IPTC; XMP keywords override all other keyword sources (including folder-name-derived); changes by other tools are picked up on reindex only if the file modification date changed — [PhotoPrism metadata docs](https://docs.photoprism.app/user-guide/library/metadata/)

**Capture One / Photo Mechanic**
- Capture One supports hierarchical keyword lists; assigning a child keyword adds all parents; stores keywords in XMP sidecars by default for RAW; embeds in JPEG/TIFF on export; does not embed in exported unprocessed RAW — [Capture One support article 360002544178](https://support.captureone.com/hc/en-us/articles/360002544178)
- User report: Photo Mechanic hierarchical keyword edits were recognized by both PM and Capture One, but after opening in Capture One 8.3.2 some hierarchical paths were gone and pipe-separated dc:subject entries were reduced to single keywords (single report, old version) — [Capture One community, "Hierarchical keyword problem xmp sidecar"](https://support.captureone.com/hc/fr/community/posts/360012252278-Hierarchical-keyword-problem-xmp-sidecar)
- 2015 report: Photo Mechanic keyword changes showed up correctly in Capture One via XMP — [photools.com community](https://photools.com/community/index.php?msg=33128)

**Apple Photos export**
- "Export Unmodified Original" + "Export IPTC as XMP" writes keywords to a sidecar; edits are not exported (proprietary anyway); forum reports conflict on whether Lightroom reads sidecars for JPEGs (one: LR only reads .xmp sidecars for raws; another found no difference; a Photo Joseph commenter says Photoshop/LrC/ON1 read it) — [Adobe Community, "Optimally importing selected photos from Apple Photo into Lightroom Classic"](https://community.adobe.com/t5/lightroom-classic-discussions/optimally-importing-selected-photos-from-apple-photo-into-lightroom-classic-on-a-mac/m-p/14703710/highlight/true); [Adobe Community, "Apple Photos exports of JPEGs: are XMPs importable"](https://community.adobe.com/t5/lightroom-classic-discussions/apple-photos-exports-of-jpegs-are-xmps-importable/m-p/8813522); [photojoseph.com comment](https://photojoseph.com/comment/34740)
- Standard "Export Photos" (edited version) embeds keywords in the JPEG/TIFF; check "include keywords and titles" and optionally location; dragging out of Photos loses keywords and exports at lower quality — [Adobe Community](https://community.adobe.com/t5/lightroom-classic-discussions/optimally-importing-selected-photos-from-apple-photo-into-lightroom-classic-on-a-mac/m-p/14703710/highlight/true)
- Face names: Photos can export face names as keywords in `XMP:Subject` via Unmodified Original + IPTC-as-XMP; the sidecar omits album info and face *locations*, which live in Photos' photos.db sqlite database; the osxphotos tool exports face rectangle coordinates plus name (not eye/mouth points); community members say Face IDs "only work within the Photos system" but keywords/captions travel — [Lightroom Queen forum](https://www.lightroomqueen.com/community/threads/how-do-i-import-mac-face-tages-as-lrc-people-keywords.42716/); [ExifTool forum, "Apple Photos App Metadata"](https://exiftool.org/forum/index.php?msg=47658); [Adobe Community, "including face recognition data when importing Apple Photos library"](https://community.adobe.com/t5/lightroom-classic-discussions/including-face-recognition-data-when-importing-apple-photos-library/m-p/14641034/highlight/true)
- PhotoPrism documents an Apple Photos migration use case — [PhotoPrism Apple use case](https://docs.photoprism.app/user-guide/use-cases/apple)

### Inferences
- A "portable minimum" that every app in the sources reads: `XMP-dc:Subject` (flat keywords, also mirrored to IPTC:Keywords), `XMP:Rating`, `EXIF:DateTimeOriginal`, `XMP-dc:Description`. Write hierarchical keywords too (both `lr:HierarchicalSubject` and `digikam:TagsList`) so that LrC, digiKam, and Immich all pick the hierarchy up, but *also* flatten the leaf nodes into dc:Subject so the data survives apps that read only flat keywords (the MWG 2.0 flattening rule). ExifTool can write all forms in one pass.
- Encode family branch as a hierarchy leaf whose flat form is self-explanatory, e.g. `People|Family|Smith side|Jane Smith` → flat keywords "Jane Smith" and "Smith side". The flat leaf is what Apple Photos, PhotoPrism's simple XMP reader and Immich's IPTC fallback will see.
- Face *regions* are the least portable element: names survive as keywords everywhere; rectangles survive LrC↔digiKam via mwg-rs but not into Apple Photos (which re-detects) and only uncertainly into Immich. Plan on names-as-keywords as the durable truth and treat rectangles as app-local convenience.
- For RAW and video, sidecars are mandatory (apps won't write into RAW/video containers); for JPEG/HEIC embedded XMP is more durable because the sidecar can be separated from the file. digiKam's "write to sidecar for read-only items only" mode is the pragmatic middle.
- All-Apple household implication: Apple Photos is a fine *viewer* but a poor *system of record* for metadata, since face regions and albums never leave its database and keywords only exit via export. If Photos stays the family's daily app, add people names as keywords inside Photos so they are exportable.

- Photo Mechanic's own documentation on which keyword fields it writes was not found; only user reports.

## Key Question 3: Document organization frameworks for business vs personal (PARA, Johnny.Decimal, simple top-level split) and what should live where in a Zoho WorkDrive / Google Drive / iCloud setup

### Takeaway
PARA sorts by actionability (Projects / Areas / Resources / Archives) and is deliberately flexible; Johnny.Decimal sorts by a fixed numbered taxonomy (≤10 areas × ≤10 categories × ≤100 IDs, "only two levels deep") and is deliberately rigid; practitioners frequently combine them. For a two-tenant setup the sources support a hard top-level split by *ownership/tenant* (business on WorkDrive, personal on iCloud/Google) with PARA or JD applied *inside* each, and the NAS holding archive and backup copies rather than working files.

### Cited Findings
- PARA is "a folder-based, action-oriented method that sorts files into Projects, Areas, Resources, and Archives"; its premise (Forte, Building a Second Brain) is that files are only useful if you can discover and use them again; projects move easily between folders — [Recall summary of Zsolt's Visual PKM](https://www.recall.it/summary/zsolts-visual-pkm/the-ultimate-guide-to-file-organization-5-systems-you-must-know); [Crystal Lee, "Two approaches to PKM"](https://crystaljjlee.mataroa.blog/blog/two-approaches-to-pkm/)
- PARA definitions: Projects = specific short-term efforts with a goal; Areas = ongoing responsibilities (health, finances) that encompass projects; Resources = reference on topics of interest; Archives = anything inactive from the other three; the term originates in Chapter 5 of Building a Second Brain (2022) with a dedicated book The PARA Method (2023); Areas vs Resources is the commonly confused boundary — [Lark, "What is the PARA method"](https://www.larksuite.com/es_mx/blog/para-method); [Goodreads note on The PARA Method](https://www.goodreads.com/notes/123394685-the-para-method/69303284-george-guimar-es/b59bc470-f83a-4897-8eb5-da711a024290)
- Johnny.Decimal official rules: max 10 areas (00-09 … 90-99), each area holds up to 10 categories, each category up to 100 IDs (.00–.99); "We don't store anything in areas or categories. Only in IDs", so everything is "only two levels deep"; an index lists all numbers — [johnnydecimal.com, "The numbers"](https://johnnydecimal.com/documentation/the-numbers.md); [johnnydecimal.com introduction](https://johnnydecimal.com/documentation/introduction)
- Third-party JD practice: always two-digit IDs for sorting, no folders below the category level, maintain an index; JD "was designed to address the problem of deeply nested folder structures" and is tool-agnostic (file system, cloud drive, email, notes) — [dsebastien.net, "Organize Anything With The Johnny Decimal System"](https://dsebastien.net/blog/2022-04-29-johnny-decimal); [Ben Wilson on Johnny.Decimal](https://world.hey.com/merovex/the-johnny-decimal-system-organizing-your-digital-life-or-company-aa15af78)
- Comparison: one user describes PARA as flexible and JD as "much more strict and easy to find"; JD has a ceiling of 99 items per category; a composer adopted JD partly to avoid Windows path-length limits from nested folders and found it "taxonomical versus philosophical"; one blogger went JD→PARA→back to modified JD; combining is common ("Areas can align with PARA categories within a JD structure") — [vi-control forum case study](https://vi-control.net/community/threads/folder-hierarchy-and-data-organization-a-case-study-older-proprietary-system-vs-the-para-system.133344/); [www-gem system structure](https://www-gem.codeberg.page/sys_structure/); [stonecharioteer TIL](https://tech.stonecharioteer.com/posts/2021/til-johnny-decimal-organization-system)
- Zoho WorkDrive is a team/tenant product with Admin Console controls (data retention, deleted items) that only the business admin manages — [Zoho WorkDrive Data Retention Policy](https://help.zoho.com/portal/en/kb/workdrive/teams/admin-console/settings/articles/data-retention-policy)
- Zoho WorkDrive TrueSync (Mac and Windows; Mac min OS X 10.14 at time of post) keeps files "online-only" by default (no disk space; downloaded on open) or "available offline" (stored locally, edits sync back) — [Zoho community, WorkDrive TrueSync](https://help.zoho.com/portal/en-gb/community/topic/workdrive-truesync?page=4); [Zoho community, Introducing TrueSync](https://help.zoho.com/portal/ja/community/topic/new-in-workdrive-introducing-true-sync-for-windows-beta)
- Google Drive versioning: older versions auto-removed after 30 days or once 100 newer versions exist (whichever first) unless "Keep forever" is set; deleted files sit in Trash 30 days — [U-Michigan, "Google: Managing Drive File Versions and History"](https://teamdynamix.umich.edu/TDClient/30/Portal/KB/Article/12539/Google-Managing-Drive-File-Versions-and-History); [Google Workspace Updates, trash auto-delete 30 days (2020)](https://workspaceupdates.googleblog.com/2020/09/drive-trash-auto-delete-30-days.html?hl=pt_BR); [mediaatelier cloud sync comparison](https://www.mediaatelier.com/en/Posts/Cloud-Sync-Comparison-Version-History/)

### Inferences
- Tenant first, framework second: because WorkDrive's retention, trash and sharing are governed by a business admin console and the personal clouds are governed by Apple/Google consumer rules, the top level must be *who owns the data* (Business → WorkDrive; Personal/Family → iCloud Drive or Google Drive). Mixing them in one tree breaks on permissions, tax/records retention, and eventual business sale/closure.
- Inside each tenant, PARA's four buckets suit *documents* (Projects/Areas/Resources/Archive) while JD's numbering suits *reference material that must be found by others* (contracts, policies, manuals). A workable hybrid for a small business on WorkDrive: Team Folders named with JD areas (10-19 Admin & Legal, 20-29 Finance, 30-39 Clients, 40-49 Marketing…), with a `Projects` and `Archive` Team Folder following PARA. Personal: `Personal / Family / Archive` with PARA inside Personal.
- "Working set" = the cloud drive that syncs to the Mac (WorkDrive TrueSync "available offline" for active business folders; iCloud Drive for personal); "archive" = NAS share organized by year or JD number (read-mostly); "backup" = NAS snapshots + HBS 3 off-site + cold SSD (Question 5). Never let the NAS be the working set for Apple-specific bundles (Photos library, FCP library) — see Questions 4–5.
- Because Google Drive's version history is capped at 30 days/100 versions and iCloud Drive's is uncertain-to-absent, neither cloud substitutes for versioned backup of documents; the NAS (snapshots) or HBS 3 versioning must provide the long version history.

## Key Question 4: Video projects — folder templates for Final Cut Pro / DaVinci Resolve / Premiere, local SSD vs NAS, library management and proxies

### Takeaway

## Key Question 5: 3-2-1 / 3-2-1-1-0 backup design for a home user with QNAP NAS, iCloud+ 200 GB, Google One, Zoho WorkDrive and portable SSDs (no new subscriptions)

### Takeaway
The sources support: live data on the Mac + QNAP (snapshots as fast rollback and ransomware defense), Time Machine to the QNAP over SMB 3, HBS 3 jobs pushing a client-side-encrypted, versioned copy of the archive to Google Drive as the off-site copy (subject to Google One quota, a ~750 GB/day upload cap, and slow per-file API throttling for many small files), and a rotated cold SSD/HDD as the air-gapped "1". iCloud Photos and iCloud Drive are sync, not backup (deletions propagate, 30-day recovery, weak/no versioning), and Zoho WorkDrive offers unlimited versions and configurable trash retention but no native export-to-NAS, so a NAS pull via WebDAV/rclone or a locally synced "offline" folder is the only way to get a business copy under your own control.

### Cited Findings
**Rules**
- 3-2-1-1-0: 3 copies, 2 media types, 1 off-site, 1 immutable/air-gapped (added because ransomware now targets connected backups, off-site copies and backup credentials first), 0 errors (restore tests verify backups work); the original 3-2-1 is usually credited to photographer Peter Krogh — [Zmanda, "Understanding the 3-2-1-1-0 Backup Rule"](https://www.zmanda.com/blog/understanding-the-3-2-1-1-0-backup-rule/); [AvePoint, "What Is the 3-2-1 Backup Rule? (And Why It's Evolved to 3-2-1-1-0)"](https://www.avepoint.com/blog/backup/what-is-the-3-2-1-backup-rule); [tecsens 3-2-1-1-0](https://www.tecsens.com/en/3-2-1-1-0-baas-policy/)
- QNAP's own ransomware guidance: 3 copies, ≥2 media types, 1 off-site; HBS can copy data or snapshots to another NAS, remote server, cloud, expansion unit or external drive — [QNAP ransomware solution page](https://www.qnap.com/solution/ransomware/de/); [QNAP home snapshots](https://www.qnap.com/en-uk/solution/home-snapshots)

**QNAP snapshots (QTS / QuTS hero)**
- Snapshots are block-level and "separate from the file system and remain safe even if the file system is affected by ransomware"; max snapshot count depends on model and RAM; "guaranteed snapshot storage" reserves space so a set number are always kept; QNAP's only frequency guidance is "A snapshot a day keeps data loss away!" — [QNAP home snapshots](https://www.qnap.com/en-uk/solution/home-snapshots)
- QNAP recommends multiple snapshot versions and replicating snapshots to a second QNAP NAS; default snapshot reservation is 20% — [QNAP snapshots solution page](https://www.qnap.com/en-as/solution/snapshots)
- QTS = Linux/ext4 for entry/mid-range models; QuTS hero = ZFS for high-end models; a 2023 third-party chart rates QuTS hero higher on data security (self-healing, copy-on-write) and power-failure protection; switching OS requires full reinstall — [Broadband Buyer, "QTS vs QuTS hero"](https://www.broadbandbuyer.com/Advice/4624-qnap-qts-vs-quts-hero-what-the-difference/); [techtest.org comparison](https://techtest.org/qts-hero-und-qts-5-im-vergleich-wo-liegen-die-unterschiede-und-welches-ist-schneller/)
- On QuTS hero shared folders are created in Storage & Snapshots and can be snapshotted per shared folder as well as per pool (user report) — [QNAP community, "QuTS Hero First Thoughts"](https://community.qnap.com/t/quts-hero-first-thoughts/931)

**HBS 3 → Google Drive**
- HBS 3 backs up NAS data to Google Drive and restores it: add Google Drive as a storage space, authorize, create a backup job with schedule, file versioning ("keeps multiple versions of files as needed") and include/exclude filters — [QNAP FAQ, "How do I back up data to Google Drive using HBS3 and restore it"](https://www.qnap.com/en-ca/how-to/faq/article/how-do-i-back-up-data-to-google-drive-using-hbs3-and-restore-it)
- Client-side encryption is a job Policy that encrypts before sending; once applied it "cannot be disabled, and the password cannot be changed" — losing the password loses the backup; encryption can be combined with QuDedup — [QNAP HBS 3 docs: creating a backup job](https://docs.qnap.com/application/hybrid-backup-sync/3v21.x/en-us/creating-a-backup-job-753C8301.html); [QNAP HBS 3 docs: jobs](https://docs.qnap.com/application/hybrid-backup-sync/3v21.x/en-us/jobs-B864C9AA.html); [QNAP blog HBS3 highlights](https://blog.qnap.com/hbs3-highlights-en/)
- When version management is on and the destination is a remote server/cloud, HBS 3 may auto-enable QuDedup, producing `.qdff` containers instead of readable filenames; QNAP advises not enabling versioning and QuDedup together if you want a browsable file structure; integrity quick checks are unavailable for NAS-to-NAS jobs with QuDedup off — [QNAP FAQ, "Why does HBS 3 apply QuDedup automatically"](https://www.qnap.com/en-gr/how-to/faq/article/why-does-hbs-3-apply-qudedup-deduplication-automatically-in-some-backup-jobs)
- Google changed the Drive API on 2024-10-30; QNAP requires HBS 3 25.1.2.692 or later for Google Drive sync to keep working — [QNAP community notice](https://community.qnap.com/t/update-hbs-now-to-sync-with-google-drive-please-note-that-google-has-updated-the-api-without-prior-notification/136)

## Key Question 6: Deduplication and consolidation — tools to find duplicates across old folder trees and strategies for merging years of manual folders into a date-based master archive without losing the "which family" information

### Takeaway
Run content-hash dedup (dupeGuru/czkawka/fclones/rmlint) on the raw folder trees first, then perceptual/similar-image dedup (czkawka "similar images", PhotoSweeper for Apple Photos/Lightroom/Capture One libraries, Gemini 2 or PowerPhotos for Photos libraries), and before moving anything convert the old folder path into keywords with a single recursive exiftool command (`"-subject<directory" -sep "/" -r`) so family/event names survive the move into YYYY/YYYY-MM-DD folders.

### Cited Findings
- exiftool one-liner from Phil Harvey: `exiftool "-subject<directory" -sep "/" -r DIR` writes each path component as a separate XMP:Subject keyword (also adds the top folder name, preserves `_original` backups); variants: `-api listsplit="[/ ]"` to split on spaces too; regex to keep only the last folder and strip a `YYYY-MM-DD ` prefix: `"-Subject<${Directory;s/.*\/([^\/]*$)/$1/;s/\d{4}-\d\d-\d\d\s*//;s/_/ /}"`; `-+subject` with `-api nodups` appends without duplicates; pass the folder path, not `*` or `.`; Harvey recommends XMP:Subject over IPTC:Keywords; `-overwrite_original` suppresses backups — [ExifTool forum, "Embedding folder names as keywords"](https://exiftool.org/forum/index.php?msg=49360); [ExifTool forum, "Use parts of the folder names as keywords"](https://exiftool.org/forum/index.php?msg=85824); [ExifTool forum, "Multiple adding to jpg files tags from folder name"](https://exiftool.org/forum/index.php?msg=69963); [ExifTool forum, "Move existing folder name into image tag"](https://exiftool.org/forum/index.php?msg=41972)
- Lightroom Classic has no built-in folder-to-keyword conversion; users ask for it in the community — [Adobe Community, "is there a way to create keywords in LrC based on folders"](https://community.adobe.com/questions-675/is-there-a-way-to-create-keywords-in-lrc-based-on-folders-and-sub-folders-977542)
- dupeGuru: free, open source, scans multiple drives, matches by name/size/content; has a photo mode with fuzzy content matching; strongest for exact duplicates — [SaaSHub dupeGuru reviews](https://www.saashub.com/dupeguru-reviews); [Hands-On Tech podcast on de-duping photos](https://pod.wave.co/podcast/all-twittv-shows-audio/hands-on-tech-228-de-duping-photos-on-macos-ad369393)
- czkawka: Rust, multi-threaded, finds duplicates, invalid symlinks and similar images (adjustable min size and similarity level), Linux/macOS/Windows; three frontends — czkawka_cli, czkawka_gui (GTK4, maintenance mode) and Krokiet (Slint, actively developed); an HN commenter moved from dupeGuru to czkawka for better comparison interface and speed — [Linux Uprising on Czkawka](https://linuxuprising.com/2021/03/find-and-remove-duplicate-files-similar.html); [rustutils czkawka](https://rustutils.com/tools/czkawka/); [AlternativeTo PhotoSweeper alternatives](https://alternativeto.net/software/photosweeper)
- rmlint: Linux-only CLI for duplicates, temp files, etc. — [AlternativeTo Czkawka](https://alternativeto.net/software/czkawka/?p=3)
- PhotoSweeper (Mac): v5 released summer 2025, $15 one-time (store listing April 2026: $14.99, v5.5.1); works with Apple Photos, iPhoto, Aperture, Capture One and Lightroom Classic libraries plus folders/external drives; duplicates in Apple Photos go to a special album, in Lightroom are marked rejected; free trial limits deletion; three review modes — [AppAddict PhotoSweeper review](https://scour.ing/@AnnaMaria/p/https://appaddict.app/post/photosweeper-powerful-adaptable-affordable-one-time-purchase); [pcmacstore PhotoSweeper listing](https://pcmacstore.com/en/app/463362050/photosweeper)

- Library of Congress: where several versions of one image exist, keep the highest-quality copy — [LOC personal archiving photos](https://www.digitalpreservation.gov/personalarchiving/photos.html)

### Inferences
- Migration order that preserves information: (1) full backup/snapshot of the old trees; (2) exact-dup pass (czkawka/dupeGuru) keeping the copy in the most descriptive folder; (3) exiftool folder-path→keywords pass on the *remaining* files (so family/event names become `XMP:Subject`, with the `-api nodups` form so reruns are safe); (4) exiftool or your DAM's import renames/moves into `YYYY/YYYY-MM-DD` using `DateTimeOriginal` (fallback to FileModifyDate for scans, flagged with a `needs-date` keyword); (5) similar-image pass (czkawka similarity / PhotoSweeper) inside the new tree where near-duplicates now sit side by side by date; (6) only then import into the catalog (LrC/digiKam/Immich) which will read the keywords.
- Folder names like "Smith family/Christmas 2019" become keywords "Smith family" and "Christmas 2019"; post-process the vocabulary once (map "Smith family" → hierarchy `People|Family|Smith side`) with an exiftool `-subject-=... -subject+=...` batch or in the DAM's keyword manager.
- For files inside an Apple Photos library, do not dedup on the filesystem; use Photos' Duplicates album, PowerPhotos or PhotoSweeper (which understand the library database) and export originals + IPTC-as-XMP afterwards.

## Key Question 7: Ongoing-maintenance budget — routines (weekly inbox triage, monthly tag review, annual archive) and automation that keeps the system alive with minimal effort

### Takeaway
No single authoritative schedule exists; practitioners converge on a short weekly pass driven by a smart album/filter ("last 7 days, no title/keyword"), a monthly duplicate/keyword check, and a yearly cull of one prior year, with automation (import presets that apply date folders and keywords, NAS snapshot schedules, scheduled HBS 3 and rclone jobs, smart albums) carrying the rest.

### Cited Findings
- Weekly: a smart album showing photos from the last 7 days without a title; each is deleted or titled/keyworded and drops out when done, so an empty album means the week is finished — [Jamie Rubin, "The Weekly Playbook #2: Curating Photos"](https://jamierubin.net/2021/07/09/the-weekly-playbook-2-curating-photos/)
- Monthly/quarterly: review the collection periodically for new duplicates; scheduled check-ins to confirm new photos fit the structure, delete unneeded photos, update tags — [The Tech Edvocate, "How to organize photo library"](https://www.thetechedvocate.org/how-to-organize-photo-library/)
- Yearly: a photographer with ~60,000 images picks one year each winter, builds 1:1 previews, reviews each image for seconds, flags rejects, then deletes them in one grid pass — [Complete Digital Photography, "Managing your photo library: pruning old growth"](https://completedigitalphotography.com/2020/01/pruning-old-growth-photos/)
- Once the backlog is done, apply the same workflow to new photos in small batches — [O'Reilly, Declutter Your Photo Life, ch. 16 "Maintaining Your Photo Archive"](https://www.oreilly.com/library/view/declutter-your-photo/9781681988764/xhtml/chapter16.xhtml)
- Minimalist stance: keep fewer photos; aggressive culling reduces all downstream maintenance — [birdhouse.org, "the minimalist approach to photo collections"](https://blog.birdhouse.org/2024/01/01/the-minimalist-approach-to-photo-collections/)
- Apply keywords at import to the whole batch, then touch up (Carlson) — [TidBITS, Take Control chapter](https://tidbits.com/?p=13946)
- Automation available: digiKam lazy sync + scheduled writes; Immich SYNC/DISCOVER sidecar jobs; Resolve Python API bin scripting; HBS 3 scheduled jobs with filters; QNAP snapshot schedules; Lightroom auto-write XMP — [digiKam Metadata Settings](https://docs.digikam.org/setup_application/metadata_settings.html); [Immich XMP sidecars](https://docs.immich.app/features/xmp-sidecars); [tryuncle Resolve template](https://tryuncle.com/learn/davinci-resolve/how-to-create-a-project-template-in-davinci-resolve); [QNAP HBS3 Google Drive FAQ](https://www.qnap.com/en-ca/how-to/faq/article/how-do-i-back-up-data-to-google-drive-using-hbs3-and-restore-it); [Adobe Community on auto-write XMP](https://community.adobe.com/t5/lightroom-classic-discussions/possible-to-embed-face-data-with-lr-classic/m-p/12238821)

### Inferences
- Budget that the sources support: ~15 min/week (triage last 7 days: delete, rate, add People/Event keyword via smart album or Immich "untagged" filter), ~30 min/month (run duplicate scan on the inbox, review new keywords against the controlled list, confirm HBS 3 and Time Machine jobs succeeded, rotate the cold SSD), ~2 h/year (cull one old year, verify checksums/scrub, test-restore one folder from Google Drive and one snapshot, archive finished video projects: delete generated files → consolidate → move to NAS).
- Everything that can be done at *import* (date folder, rename, base keywords, GPS) should be, because the forum failure reports are all about retroactive tagging never happening.
- A single "Inbox" folder on the NAS/Mac that the weekly routine empties is the only manual folder maintenance left; the date tree below it is machine-generated.
